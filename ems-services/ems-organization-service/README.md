# Organization service

Spring Boot service for locations and departments, using Java 17+ and PostgreSQL.

## Run

To start the complete service and its own PostgreSQL database locally:

```sh
docker compose up --build --wait
```

The API is available at `http://localhost:8087`. Set `ORGANIZATION_PORT` to change
the host port and `DB_PASSWORD` to override the local database password. The
database is private to the Compose network, and its data persists in the
`organization-data` volume. `docker compose down` stops the stack and preserves
data. This standalone stack does not depend on the platform Compose file.

To run directly with Maven instead:

Create an empty PostgreSQL database and configure `DB_URL`, `DB_USERNAME`, and
`DB_PASSWORD`. Defaults are `jdbc:postgresql://localhost:5432/ems_organization_db`,
`organization_user`, and `organization_password`. Then run:

```sh
./mvnw spring-boot:run
```

Flyway applies migrations at startup and Hibernate validates the resulting schema.
The API listens on port 8080 by default (`SERVER_PORT` overrides it).

`GET /actuator/health/liveness` checks application liveness, and
`GET /actuator/health/readiness` also checks database connectivity. Only health
endpoints are exposed; database and infrastructure details are omitted.
Shutdown is graceful, with up to 20 seconds to finish active requests.

## API

The OpenAPI 3 contract is served at `/openapi.json` and is stored in
[`src/main/resources/static/openapi.json`](src/main/resources/static/openapi.json).

| Method | Path                               | Behavior                                                          |
| ------ | ---------------------------------- | ----------------------------------------------------------------- |
| POST   | `/api/locations`                   | Create a location; 201 with a Location header                     |
| GET    | `/api/locations`                   | List locations in ascending ID order                              |
| GET    | `/api/locations/{id}`              | Retrieve a location                                               |
| PUT    | `/api/locations/{id}`              | Replace its name                                                  |
| DELETE | `/api/locations/{id}`              | Delete an empty location; 204                                     |
| POST   | `/api/departments`                 | Create a department; 201 with a Location header                   |
| GET    | `/api/departments?locationId={id}` | List all departments or filter by location, in ascending ID order |
| GET    | `/api/departments/{id}`            | Retrieve a department and its location details                    |
| PUT    | `/api/departments/{id}`            | Replace its name and location                                     |
| DELETE | `/api/departments/{id}`            | Delete a department; 204                                          |

Location create/replace bodies contain `{"name":"Calgary"}`. Department
create/replace bodies contain `{"name":"Operations","locationId":1}`.
PUT requires all fields. Names are required, must contain non-whitespace text,
and must be at most 100 characters as submitted. Surrounding whitespace is
removed before storage, while display casing is preserved. IDs must be positive.
JSON names must be strings and JSON IDs must be integers. Fractional IDs,
numeric strings used as IDs, duplicate JSON keys, and trailing JSON documents
are rejected with 400 instead of being silently coerced or ignored.

Location names and department names are each globally unique, ignoring case.
A department can move to another existing location. Filtering by a location
without departments, including an unknown location, returns an empty array.
Deleting a missing record returns 404; deleting a location with departments
returns 409. Deleting a department preserves its location. References held by
other microservices are not checked by this service.

Invalid requests return 400, missing records return 404, and duplicate names,
foreign-key conflicts, and concurrent update conflicts return 409. Errors use
the shared `ApiErrorResponse` shape with `timestamp`, `status`, `code`, `message`,
`path`, and field-level `errors`.
Unknown routes (404), unsupported methods (405), and unsupported content types
(415) use the same error shape. Unexpected failures return a generic 500 response
and are logged on the server. Authentication and role authorization are not
implemented in this service; no authorization rules were specified for its API.

V2 adds case-insensitive database indexes to protect concurrent writes. Existing
names that differ only in case must be resolved before applying V2; the migration
does not rename or delete existing records.

## Tests

```sh
# Unit tests and Spring MVC API tests; no database or Docker required
./mvnw test

# Also run full application tests against an isolated PostgreSQL 18 container
# Requires a running Docker daemon; pulls postgres:18-alpine if needed
./mvnw -Pintegration verify
```

The integration profile fails when Docker is unavailable instead of silently
skipping database checks. It never uses the configured application database.
Tests cover CRUD, validation boundaries, duplicate names, missing records and
parents, moving departments, deletion restrictions, migration/startup, auditing,
rollback, database uniqueness/foreign keys, and optimistic locking.
The PostgreSQL tests also start the HTTP server on a random port, exercise real
network requests, verify health probes, and race two case-insensitive creates.
